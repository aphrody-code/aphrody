# GUI options for aphrody — 2026 landscape and recommendation

Research-only document. Compares the best 2026 options for building a graphical
UI for aphrody across two families: (1) **Rust-native** GUI toolkits, and
(2) GUI surfaces **driven by Bun**. Concludes with an actionable ranking for
aphrody's specific context.

Author: aphrody-code. Last updated: 2026-05-23.

---

## 0. aphrody constraints that drive the decision

These are hard inputs, not preferences:

1. **Platform priority (strict)**: Linux Ubuntu 26.04 = #1, Windows 11 = #2,
   WebAssembly (lib) = #3, macOS = best-effort. A toolkit that is not solid on
   Linux is disqualified as a primary, regardless of how good it is elsewhere.
2. **License**: aphrody is Apache-2.0 with a **zero-GPL / zero-LGPL** policy
   (same rule that bans `unicorn-engine`, see `CLAUDE.md` §7). Any GPL/LGPL
   contamination — even transitive and even if "no-op at runtime" — is a hard
   block for code linked into the distributed binary.
3. **Existing investment** (already shipped, must be weighed):
   - `crates/aphrody-ffi` — a `cdylib` exposing a stable C ABI over the *entire*
     CLI surface (`aphrody_run`, `aphrody_run_json`, `aphrody_run_captured`,
     plus error/version symbols). FFI call cost measured at p50 ~0.5 ms.
   - `@aphrody-code/native` — a Bun `bun:ffi` bridge that calls that cdylib
     in-process (no subprocess).
   - `@aphrody-code/console` — a `Bun.serve` server + browser frontend styled
     with Material 3 tokens, driving the whole CLI live.
   - Design system "M3 fusion": Material Web (Lit web components) + `m3-react`
     (React 19) + M3 tokens generated by `aphrody design tokens --fusion`.
     Aesthetic target = Material Design 3 / Google Sans / Gemini look.
   - Native-side M3 work already exists but was **extracted** on 2026-05-23 to
     the sibling repo `C:\src\aphrody-ts\rust-ui`: the `gui` crate
     (winit + wry/tao + wgpu, sharing `m3-tokens`) and the `mui-rs*` stack
     (`mui-rs-renderer` = Vello 2D + wgpu + Taffy + Parley — a from-scratch M3
     GPU renderer). These were removed from the CLI workspace to keep the core
     build lean.
   - `m3-tokens` and `aphrody-icons` crates **remain** in this repo and are the
     canonical token/icon source for any surface (native or web).

The single most important consequence: **aphrody already has a working,
M3-styled, web-tech GUI path that reuses the FFI bridge.** The question is less
"which toolkit from scratch" and more "is there a reason to leave the
web-tech + FFI path, and if we package it, how."

Notes that materially affect aphrody:

- **egui / iced / Makepad / GPUI** render their *own* visual language. Matching
  MD3 means re-skinning by hand and re-building MD3 components — the
  `mui-rs-components` effort proved this is a large, ongoing cost. They do not
  consume Material Web or `m3-react`.
- **Dioxus(Blitz), Freya, Xilem, Floem, Vello+winit** are all built on the same
  shared Rust UI stack (some subset of Taffy layout, Parley text, Vello/Skia
  render, AccessKit, winit). This is the healthy, converging native ecosystem,
  but the **component/theming layer for MD3 does not exist off-the-shelf** in
  any of them — aphrody would author it (which is exactly what `mui-rs` was).
- **Tauri v2** is the only native-Rust option where the M3 fusion design system
  (Material Web Lit components + tokens + optionally `m3-react`) runs verbatim,
  because the frontend is a real webview. The Rust side stays in control of the
  process and can link `aphrody-ffi` directly.

### 1.2 License flags (hard gate)

- **GPUI — BLOCKED for aphrody.** Declares `license = "Apache-2.0"`, but a
  default release build statically links GPL-3.0-or-later object code through
  `gpui -> sum_tree -> ztracing -> zlog` (`+ ztracing_macro`). Any binary
  depending on gpui inherits GPL-3.0 source-availability + share-alike
  obligations; GPL-3.0 is asymmetrically incompatible with Apache-2.0 at the
  binary-distribution level. The GPL code is "no-op at runtime" in non-Zed
  builds, but **license obligations attach at link/distribution time, not at
  execution time** — so this does not save it. This is the same class of
  problem as `unicorn-engine` (GPL-2.0) already banned in `CLAUDE.md` §7.
  Tracked upstream as zed-industries/zed#55470. Exclude until upstream removes
  the GPL link.
- **Slint — FLAG, conditionally usable.** Triple license: GPLv3 OR Royalty-free
  OR Commercial. The **GPLv3** option is incompatible with aphrody's policy and
  would force the whole binary under GPL. The **Royalty-free** license (added
  in 1.1) permits proprietary/permissive **desktop, mobile and web** apps at no
  cost and **without royalties** — embedded is the only excluded/royalty case.
  So aphrody *could* legally use Slint on the royalty-free terms for a desktop
  GUI. However: (a) it is a vendor-controlled bespoke license, not OSI-approved,
  which complicates `cargo deny` / `cargo vet` and the Apache-2.0 supply-chain
  story; (b) accepting the royalty-free terms means **not** taking the GPL
  grant, so the source distribution is governed by Slint's terms, not Apache.
  Net: legally possible for desktop, but it injects a non-standard license into
  an otherwise clean Apache-2.0 dependency graph. Treat as "avoid unless Slint's
  tooling is a decisive win," and never via the GPLv3 grant.
- All other native toolkits in the table (egui, iced, Dioxus/Blitz, Makepad,
  Freya, Xilem/Masonry/Vello, Floem, Tauri/tao/wry, wgpu) are **MIT and/or
  Apache-2.0** — clean for aphrody. Their *transitive* trees still must pass
  `cargo deny` (e.g. the usual GTK3 CVE ignores already configured in
  `deny.toml` apply to any wry/tao Linux path).

## 2. Bun-driven GUI surfaces

aphrody already drives the CLI from Bun in-process via `bun:ffi`
(`@aphrody-code/native`). The Bun GUI question is purely about **how to put a
window around the existing M3 web frontend** while keeping that FFI bridge.

### 2.2 The Tauri-with-Bun-sidecar subtlety (important)

The brief lists "Tauri v2 with a Bun sidecar." For aphrody this combination is
usually the *wrong* shape, and it is worth being explicit about why:

- aphrody's logic is already a **Rust cdylib** (`aphrody-ffi`). A Tauri shell is
  itself a Rust process. So the Tauri backend can depend on the `aphrody`
  library crate (or load `aphrody-ffi`) and call commands **in-process**, with
  the same sub-millisecond latency the Bun bridge measures — no Bun, no
  subprocess, no IPC serialization.
- Adding a Bun sidecar on top means shipping a second runtime (a per-OS Bun
  standalone executable, ~50-90 MB each via `externalBin` with target-triple
  suffixes), spawning it, and crossing a process boundary for data that Rust
  already owns. That is pure overhead unless the UI genuinely needs Bun-only
  packages at runtime.
- Therefore: **if** the destination is a Tauri shell, prefer **Tauri (Rust
  backend) -> `aphrody-ffi` direct**, and treat Bun as a *build-time* tool
  (bundling the Lit/React frontend), not a runtime sidecar. Keep the Bun sidecar
  only for the narrow case of reusing a Bun-only runtime dependency.

This means the realistic Bun-driven options collapse to: **(a) keep
`Bun.serve` + browser**, or **(b) `webview-bun` / Electrobun** for a windowed
Bun app. Tauri is better classified as a *Rust-native* shell (§1) that happens
to host the web frontend.

## 3. Latency / performance and M3 fidelity analysis

### 3.1 Latency and footprint

- **FFI hot path is already optimal.** Whether the frontend is reached from Bun
  (`bun:ffi`) or from a Rust webview shell, command invocation is an in-process
  C-ABI call at p50 ~0.5 ms. No GUI choice improves on this; several make it
  worse by reintroducing a process boundary (Bun sidecar, Electron main/renderer
  IPC).
- **Cold start and binary size** favor system-webview and pure-web approaches:
  - `Bun.serve` + browser: near-zero added binary, instant.
  - webview-bun / Electrobun / Tauri: small shell + system webview, fast start
    (<50 ms class for Electrobun), no bundled Chromium.
  - Electron + Bun: 80-150 MB, slow start — contradicts aphrody's stated
    latency-minimal objective.
  - Pure native (egui/iced/Makepad/Vello): smallest steady-state and lowest
    *render* latency, but you pay it back in build/maintenance cost and lose M3.
- **Render performance.** For aphrody's UI (dashboards, command output, the
  LLM-first terminal) the bottleneck is **text and DOM-style layout**, not
  60-fps 3D. System webviews are more than adequate and bring mature text
  shaping, font rendering, and accessibility for free. The pure-GPU toolkits
  (Vello/wgpu, GPUI, Makepad) win on raw frame latency but that headroom is
  irrelevant for this workload — and `wgpu`/Vello are already available to
  aphrody (the WebGPU path, `crates/m3-tokens` consumers, the extracted
  `mui-rs-renderer`) for the niche where a custom GPU surface is justified.

### 3.2 Material Design 3 fidelity

This is the decisive axis given aphrody's "M3 / Google Sans / Gemini" target.

- **Webview / browser path = highest fidelity, lowest cost.** Material Web (Lit)
  + `m3-react` + `aphrody design tokens --fusion` already produce a faithful M3
  surface. Anything that renders real CSS/DOM (Tauri, webview-bun, Electrobun,
  `Bun.serve` + browser) inherits this *verbatim*. Google Sans, state layers,
  elevation, dynamic color, motion — all already solved in CSS/Web Components.
- **Dioxus/Blitz = medium-high.** Because Blitz renders an HTML/CSS subset, M3
  tokens and a lot of CSS can be reused, but Blitz's CSS coverage is still
  partial and experimental, so fidelity is "good, with gaps" today.
- **Pure native (egui, iced, Makepad, GPUI, Floem, Xilem, Vello+winit) = low to
  medium, high effort.** None ship MD3 components. Reaching Gemini-grade M3 means
  re-implementing the component set, state layers, motion curves, and Google Sans
  shaping against `m3-tokens` — i.e. rebuilding `mui-rs-components`. The
  `m3-tokens` crate gives you the *values*, not the *widgets*.
- **Slint = medium.** Themable and pixel-controllable, but it is its own widget
  model; an MD3 look is bespoke work, and the license caveat (§1.2) applies.

Conclusion: **the M3 design investment is a web-tech asset.** Any move to a
non-CSS native toolkit forfeits most of it. This single fact dominates the
recommendation.

## 4. Recommendation for aphrody

### Top 3 (ranked)

1. **Primary — Tauri v2 with a Rust backend calling `aphrody-ffi` directly
   (system webview hosting the existing M3 fusion frontend).**
   It is the only option that ships a real cross-platform desktop **and mobile**
   app (Linux WebKitGTK #1, Windows WebView2 #2, macOS, iOS/Android) while
   reusing 100% of the Material Web / `m3-react` / M3-token investment verbatim,
   keeps the binary tiny (no bundled Chromium), and links `aphrody-ffi`
   in-process at ~0.5 ms with no extra runtime. MIT/Apache-2.0, production-grade,
   largest ecosystem. (Do **not** add a Bun runtime sidecar — see §2.2; use Bun
   only to build the frontend.) wasm #3 is unaffected: the existing
   `aphrody-wasm` / WebGPU lib path stays independent.

2. **Alternative / keep-as-is — `Bun.serve` + system browser (today's
   `@aphrody-code/console`), optionally upgraded to a windowed `webview-bun` /
   Electrobun app.**
   Already shipped, zero added binary, full M3 fidelity, full in-process
   `bun:ffi` reuse, and the most natural fit for aphrody's "scriptable, headless,
   LLM-first" ethos — the LLM-first terminal and agent dashboards are
   browser-native. Promote to `webview-bun` or Electrobun when a genuine native
   *window* (not just a tab) is required, accepting a smaller ecosystem than
   Tauri. Best choice if the team wants to stay Bun-centric rather than grow the
   Rust shell.

3. **Niche / future-native — Xilem + Masonry (+ Vello/wgpu) for a bespoke
   GPU-rendered surface, reusing `m3-tokens`.**
   The right long-term bet *if and when* aphrody needs a pure-Rust, no-webview
   GUI (e.g. a sealed single-binary deliverable, or a custom GPU canvas the
   webview can't do). Apache-2.0/MIT, AccessKit-first, built on the same
   Vello/Taffy/Parley stack the extracted `mui-rs-renderer` already used — so the
   prior native M3 work is directly relevant. Caveat: **alpha today** and you
   own the MD3 component layer; adopt only when the webview path is proven
   insufficient.

### To avoid

- **GPUI — hard-blocked.** GPL-3.0 contamination under an Apache-2.0 label
  (§1.2); also no Windows support, killing platform #2. Do not use until
  upstream de-GPLs.
- **Slint via the GPLv3 grant — blocked** by aphrody's zero-GPL policy. (The
  royalty-free grant is *technically* usable for desktop/web but injects a
  non-OSI vendor license into a clean Apache-2.0 graph — avoid unless decisive.)
- **Electron + Bun — avoid** for a primary surface: 80-150 MB bundle and slow
  cold start contradict aphrody's latency-minimal objective; offers nothing the
  system-webview paths don't, for this workload.
- **`Bun.WebView` (built-in) and Lightpanda — not GUI options.** Both are
  headless automation/engine tools (CDP scraping / no-display browser). Valuable
  for aphrody's agent and RE surfaces, but they render no user-facing UI; don't
  scope them as GUI candidates.
- **egui / iced / Makepad / Freya / Floem as the *primary M3* GUI — avoid for
  now**, not on license grounds (they're clean MIT/Apache) but on fidelity/cost:
  each forfeits the M3 fusion web investment and forces a from-scratch MD3
  component rebuild. They remain excellent for *internal/dev* tooling where the
  Google look is not required (egui in particular for instrumentation panels).

### One-line rationale per top pick

- **Tauri v2 (Rust -> aphrody-ffi):** only path that ships desktop+mobile,
  reuses the M3 web design system verbatim, and keeps the FFI hot path
  in-process — all on a clean MIT/Apache license.
- **Bun.serve + browser / webview-bun:** already working, zero-overhead reuse of
  both the M3 frontend and the `bun:ffi` bridge, and the best match for
  aphrody's headless, scriptable, LLM-first identity.
- **Xilem + Masonry + Vello:** the credible Apache/MIT pure-Rust GPU future that
  reuses `m3-tokens` and the prior `mui-rs-renderer` work — adopt when (not
  before) a webview-free single binary is actually needed.
