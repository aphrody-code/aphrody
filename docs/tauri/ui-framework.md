# Tauri v2 frontend framework for aphrody — choosing the in-webview layer

Author: aphrody-code. Last updated: 2026-05-23.

Companion to the adoption decision in [`README.md`](README.md),
[`architecture.md`](architecture.md), [`risks.md`](risks.md), and
[`aphrody-integration.md`](aphrody-integration.md). Those docs settle the
**shell** (Tauri v2, system webview, Rust backend calling `aphrody::run_async`
in-process). This doc settles the orthogonal, finer-grained question they left
open: **which frontend framework runs inside that webview** — the
reactivity/glue layer that drives the DOM and calls Tauri IPC.

The shell choice and this frontend choice are independent: Tauri hosts a static
`dist/` of "HTML, CSS, JavaScript and possibly WASM" and is framework-agnostic
about how that `dist/` was produced ([Tauri Frontend Configuration]). It
requires only that the frontend be **static** — SSG / SPA / MPA, **no SSR**
([Tauri Frontend Configuration]).

---

## 0. The decision in one screen

**Primary: keep the current model — Vanilla TypeScript + Material Web (Lit)
web components directly, built by Bun into a static `dist/`.** This is exactly
what `apps/console` already is (three files: `app.ts`, `index.html`,
`server.ts`; the frontend imports `@aphrody-code/theme/tokens.css` and drives
the CLI — `C:\src\aphrody-ts\apps\console\src\app.ts`). It has the smallest
bundle, zero framework runtime in the webview, no SSR to disable, and renders
the M3 fusion verbatim because `md-*` components are framework-agnostic custom
elements ([Material Web], built on [Lit]).

**Alternative (adopt only when app-state complexity demands it): Lit as the
*app* framework** (not just the component lib) — `LitElement` + `@lit/context`
+ signals for views/routing, still pure web components, ~5–7 KB of runtime,
same toolchain, same Material Web, zero interop tax.

**To avoid as the primary: React 19 + `m3-react`** (heaviest runtime in a
webview whose weakest engine is Linux #1; `@lit/react` wrappers are now
redundant since React 19 scores 100% on [Custom Elements Everywhere]) and the
**Rust→wasm frameworks** (Leptos/Dioxus/Sycamore — large wasm payload, and
custom-element/Lit interop forces manual `wasm-bindgen`/`web_sys` glue for every
object-valued property, re-introducing exactly the friction Tauri+web removes).

The throughline matches every prior aphrody doc: **the M3 investment is a
web-tech asset that lives in framework-agnostic custom elements; the right
frontend layer is the one that adds the least between those custom elements and
the webview.** With Material Web now in **maintenance mode** ([Material Web is
in maintenance mode]), betting on a thin, standards-based layer (Vanilla/Lit) is
also the lowest strategic risk: it depends on the platform (custom elements +
Lit, both stable/maintained), not on a heavy framework wrapped around a frozen
component set.

## 1. What "reuse the existing investment" actually means (verified)

The constraint is to reuse aphrody's M3 fusion. Reading the real packages in
`C:\src\aphrody-ts` shows what is and is not framework-bound:

| Asset | What it is | Framework binding |
|-------|------------|-------------------|
| **Material Web** (`packages/material-web`, `@material/web` 2.4.1) | The `md-*` components. `dependencies`: `lit ^2.8.0 \|\| ^3.0.0`, `@lit/context`, `tslib`. Apache-2.0. | **None** — they are standard custom elements. Work in any framework or none ([Custom Elements Everywhere]). |
| **`@aphrody-code/theme`** (`apps/theme`, `tokens.css`) | The M3 + shadcn + Tailwind v4 token CSS, generated by `aphrody design tokens --fusion`. `exports: { "./tokens.css" }`. Apache-2.0. | **None** — it is a CSS file (`--md-sys-color-*` etc.). Any framework imports it; `apps/console` imports it directly. |
| **`@aphrody-code/m3-react`** (`apps/m3-react`, React 19) | `@lit/react createComponent` wrappers + interaction primitives (View Transitions, scroll reveal, thinking/streaming). `dependencies`: `@lit/react ^1.0.8`, `@material/web ^2.4.1`. Apache-2.0. | **React-only** — and only *needed* by React. It is a convenience over the same `md-*` elements. |
| **`apps/console`** | The live UI: vanilla TS frontend + `Bun.serve` backend over `@aphrody-code/native`. `dependencies`: `@aphrody-code/native`, `@aphrody-code/theme` — **no UI framework**. | **None** (vanilla). |
| **`crates/m3-tokens`, `crates/aphrody-icons`** | Canonical token/icon source, Rust side, **remain in this repo**. | Rust; feed both web (`@aphrody-code/theme`) and any native surface. |

The decisive structural fact: **two of the three web assets (Material Web,
`@aphrody-code/theme`) are framework-agnostic; only `m3-react` is React-bound,
and it exists solely to serve React.** "Reuse the investment" therefore does
**not** mean "use React" — it means "render `md-*` + `tokens.css`," which every
candidate can do. `m3-react` is reused **iff** the chosen framework is React;
otherwise it is simply not the relevant artifact (the components it wraps are).

Toolchain (fixed, per CLAUDE.md §2): **Bun** runtime/bundler, **oxlint** lint,
**oxfmt** format. Any candidate must build to a static `dist/` under Bun without
dragging in Node-only SSR machinery.

Notes that materially affect the ranking:

- **CE interop is no longer a differentiator among the JS options.** React 19,
  Vue, Svelte, Solid, Preact, Lit all score **100%** on [Custom Elements
  Everywhere]; React 19 specifically "uses a runtime heuristic to determine if
  it should pass data to Custom Elements as either properties or attributes."
  So **every JS candidate renders `md-*` correctly**; the differentiator is
  *weight + model + trajectory*, not "can it talk to Material Web."
- **`m3-react` only matters under React.** Choosing a non-React framework does
  not "waste" `m3-react`: the asset it wraps (Material Web) is still reused
  verbatim; `m3-react` simply stays available for any React-specific surface
  (e.g. a docs site) without dictating the Tauri shell's framework.
- **Rust→wasm forfeits the toolchain and the interop ease.** All three need
  Trunk/cargo (not Bun, CLAUDE.md §2), and Lit/Material Web interop is hand-
  wired through `wasm-bindgen`/`web_sys`/`NodeRef`, with the Leptos book
  explicitly warning that "libraries that manipulate DOM state... should be used
  with care" ([Leptos JS interop]) — Lit components own their shadow DOM, which
  is precisely that case. Object-valued component props (e.g. passing data to a
  chart or list `md-*` element) must be set imperatively per element.

## 3. Cross-webview pitfalls — WebKitGTK first (Linux #1)

The hard constraint from [`risks.md`](risks.md) §1: one frontend must render on
**WebKitGTK** (Linux), **WebView2/Chromium** (Windows), **WKWebView**
(macOS/iOS). The frontend-framework choice changes the *size and shape* of what
ships to the weakest engine; the engine itself is fixed by the shell.

### 3.1 The WebKitGTK baseline is good enough for Material Web on Ubuntu 26.04

- **Custom elements + Shadow DOM** are an open web standard implemented by all
  evergreen engines including WebKit at full parity — "Chrome, Edge, Safari, and
  Firefox now support custom elements natively with 100% parity, with no
  polyfills needed" ([Why I'm betting on the browser]). WebKitGTK is the same
  WebKit family, so the `md-*` components' core mechanism is native.
- **`ElementInternals` + form-associated custom elements** — which several
  Material Web form controls rely on — landed in WebKit (enabled by default
  from Safari Technology Preview 162, [WebKit ElementInternals]) and are present
  in current WebKitGTK. The version that matters is the engine Ubuntu ships:
  Tauri/wry binds the **`webkit2gtk-4.1`** C API ([`risks.md`](risks.md) §1.1),
  and **Ubuntu 24.04+ ships only the 4.1 line** (the 4.0 dev packages were
  removed; "Development packages were removed entirely—forcing new builds to
  target 4.1" — [WebKitGTK versions by distro]). Ubuntu **26.04** (aphrody's #1
  target) is newer still, so the engine is recent enough that `ElementInternals`
  / form-associated elements are available. This de-risks the M3 form
  components on Linux.
- **No polyfill burden for the modern path.** The `element-internals-polyfill`
  that appears in Material Web's *devDependencies*
  (`C:\src\aphrody-ts\packages\material-web\package.json`) is for legacy
  engines; on the WebKitGTK 4.1 line shipped by Ubuntu 24.04/26.04 it is not
  needed at runtime. Keeping the frontend free of a framework that re-implements
  DOM semantics (VDOM) means fewer places for a WebKitGTK quirk to surface.

### 3.2 The genuine WebKitGTK risks (independent of framework)

- **WebKitGTK lags Chromium on bleeding-edge CSS/JS** ([`risks.md`](risks.md)
  §1.2): some `:has()` / container-query edge cases and Houdini APIs. *Mitigation
  is the same regardless of framework*: target evergreen-baseline CSS (the M3
  fusion already does, via `apps/console`) and headlessly test components on
  WebKitGTK. A heavier framework does **not** help here and can hurt (more JS
  surface to differ across engines).
- **wasm cold-load is heaviest on WebKitGTK.** The Rust→wasm options ship a
  multi-hundred-KB wasm module that WebKitGTK must fetch, compile, and
  instantiate before first paint — the worst cold-start on the #1 platform,
  directly against aphrody's latency-minimal objective. The JS options (and
  especially Vanilla/Lit/Solid/Svelte) ship far less and start faster.
- **Per-engine IPC fast-path thresholds are real** (8192 B JSON on WebView2 v135,
  1024 B raw on macOS — [`architecture.md`](architecture.md) §2.2) but they live
  in Tauri's transport, *below* the frontend framework. They affect all
  frameworks identically; the lighter the frontend, the more headroom for the
  command payload itself.

### 3.3 Framework-specific custom-element gotchas (all minor, all on every engine)

- **SolidJS**: props default to attribute-style; map dash-case ↔ camelCase and
  set object props via `prop:`/ref ([solid-element], [Solid web-component
  discussion]). One-line-per-prop discipline, not a blocker.
- **Vue 3**: must declare `md-*` as custom elements via
  `app.config.compilerOptions.isCustomElement` (build-time) so Vue does not try
  to resolve them as Vue components. One config line.
- **React 19**: nothing — 100% CE interop, properties handled by runtime
  heuristic; `@lit/react` only as optional ergonomic sugar.
- **Svelte 5**: runes drive `md-*` cleanly; custom-element *output* (compiling
  Svelte → web components) is also supported but not needed here.
- **Vanilla/Lit**: nothing — this is the reference implementation of the spec.

## 4. Ranked recommendation for aphrody

### 4.1 Primary — Vanilla TypeScript + Lit/Material Web directly (continue the console model), graduating to Lit-as-app-framework if state complexity demands

Render `md-*` web components and `@aphrody-code/theme/tokens.css` directly,
wiring reactivity with the platform (DOM events + small helpers), built by Bun
into a static `dist/` that Tauri embeds as `frontendDist`. This is **already
what `apps/console` is** (`C:\src\aphrody-ts\apps\console`), so Phase 2 of the
adoption plan ([`README.md`](README.md) §6) becomes "point Tauri at the existing
console frontend," not "rebuild it in a framework."

Why it wins for aphrody:
- **Smallest bundle, fastest cold start on WebKitGTK (#1).** Zero app-framework
  runtime; only the Lit that the imported `md-*` components already pull in
  (~5–7 KB). Best fit for the latency-minimal objective on the weakest engine.
- **Zero interop tax, zero strategic coupling.** It depends only on the
  platform (custom elements + CSS) and Lit — both stable/maintained ([Lit]) —
  not on a heavy framework wrapped around **maintenance-mode** Material Web
  ([Material Web is in maintenance mode]). If a `md-*` component must later be
  forked/replaced, a thin layer absorbs it trivially.
- **Toolchain-native and ethos-aligned.** Bun + oxlint + oxfmt already build it;
  it *is* the scriptable, headless-friendly console. The same `dist/` can serve
  both the Tauri shell and the existing `Bun.serve` browser path.
- **Clean Tauri fit.** No SSR to disable, IPC via `@tauri-apps/api` or the
  `withGlobalTauri` global ([`architecture.md`](architecture.md) §4), streaming
  via Tauri `Channel` consumed by a plain JS callback.

**Graduation path (the in-doc alternative): adopt Lit as the *app* framework**
(not just components) when view/router/state complexity outgrows hand-written
DOM — `LitElement` for app shells, `@lit/context` for DI, Lit signals for
reactive state, `@lit-labs/router` for routing. This stays pure web components,
keeps the ~5–7 KB single runtime (shared with the components), keeps the exact
same Material Web + tokens + Bun toolchain, and adds **no** interop tax. It is
the natural, low-risk upgrade from vanilla without leaving the standards lane.

### 4.2 Alternative (if a mainstream JS-framework DX is wanted) — SolidJS or Svelte 5

If aphrody wants a full reactive framework's ergonomics (declarative views,
router, dev tooling) over hand-written DOM and over Lit-as-framework, pick
**SolidJS** (fine-grained signals, ~7 KB, official Tauri template, popular in
the Tauri community, signal model ideal for streaming token output) or
**Svelte 5** (compiled, ~3–10 KB, runes). Both score **100%** on [Custom
Elements Everywhere], build to static `dist/` via Vite under Bun, render `md-*`
+ tokens verbatim (modulo the one-line custom-element setup in §3.3), and stay
far lighter than React/Vue on WebKitGTK. SolidJS is the marginal pick for
aphrody because its signal-based reactivity matches streaming/agy-loop output
and it is the more common Tauri-community choice; Svelte 5 is an equally valid
choice if a compiler-first model is preferred.

### 4.3 To avoid (as the primary Tauri frontend)

- **React 19 + `m3-react` — avoid as the shell's framework.** It is the
  heaviest JS runtime (~45 KB react+react-dom) shipped to the weakest engine
  (WebKitGTK), with VDOM diffing that buys little for output panes that are
  mostly streamed text. Its historical advantage — wrappers for clean custom-
  element interop — **evaporated**: React 19 scores 100% on [Custom Elements
  Everywhere] *without* wrappers, so `@lit/react`/`m3-react` are now ergonomic
  sugar, not a necessity. Keep `m3-react` for any React-specific surface (docs
  microsite, embedding in a React host); do not let it dictate the Tauri shell.
- **Vue 3 — not wrong, but not the pick.** Clean `md-*` interop and mature, but
  ~34 KB runtime with no advantage over Solid/Svelte/Lit for this workload, and
  no existing aphrody investment in it.
- **Leptos / Dioxus / Sycamore (Rust→wasm) — avoid for *this* webview.** They
  are off-toolchain (Trunk/cargo, not Bun — CLAUDE.md §2), ship the heaviest
  cold-load on WebKitGTK (#1), and **re-introduce the exact interop friction
  Tauri-over-web removes**: Lit/Material Web components must be driven through
  hand-written `wasm-bindgen`/`web_sys`/`NodeRef` glue, with object-valued props
  set imperatively per element, and the Leptos book itself warns that DOM-state-
  manipulating libraries (i.e. Lit) "should be used with care" ([Leptos JS
  interop]). The all-Rust appeal is real, but it conflicts with both the M3-web
  reuse mandate and the latency objective. Dioxus's native **Blitz** renderer is
  a *non-webview* path that bypasses Tauri's webview and cannot render Material
  Web at all — out of scope here, and the prior native attempt (`mui-rs*`) was
  already extracted to keep the core lean ([`README.md`](README.md) §7).

## 5. Impact on the Tauri adoption plan

This refines Phase 2 of [`README.md`](README.md) §6 ("frontend + streaming") and
[`aphrody-integration.md`](aphrody-integration.md) §5 ("serving the M3 frontend")
with a concrete frontend wiring. **No change to the shell decision** (Path (a),
build-excluded `crates/aphrody-app`, in-process `aphrody::run_async`).

### 5.1 Which `apps/*` / crate is the frontend

- **The frontend is `apps/console` in the sibling repo `C:\src\aphrody-ts`**,
  evolved from "vanilla TS + `Bun.serve` for a browser" to "vanilla TS / Lit
  emitting a static `dist/` for Tauri." Concretely: keep `app.ts` driving the UI
  and rendering output, but add a build entry that emits a static `dist/`
  (HTML + bundled JS + `tokens.css`) instead of (or alongside) the `Bun.serve`
  dev path. The `Bun.serve` server (`server.ts`) stays for the standalone
  browser console; Tauri does not use it (Tauri serves `frontendDist` directly,
  no runtime server — [Tauri Frontend Configuration]).
- **No new Rust UI crate is introduced.** `crates/aphrody-app` (the Tauri shell)
  stays Rust-only and references the built `dist/` via `frontendDist`. The
  frontend source remains in `aphrody-ts` (consistent with the 2026-05-23
  extraction that moved all UI surfaces there).

### 5.2 How it consumes `@aphrody-code/theme` + Material Web

- **Tokens**: the frontend imports `@aphrody-code/theme/tokens.css` exactly as
  `apps/console` does today (`import "@aphrody-code/theme/tokens.css";` —
  `C:\src\aphrody-ts\apps\console\src\app.ts`). Tokens have one source
  (`aphrody design tokens --fusion`) feeding both the web layer
  (`@aphrody-code/theme`) and the Rust layer (`crates/m3-tokens`).
- **Components**: import the needed `md-*` elements from `@material/web` (the
  fork in `packages/material-web`) and use them directly in markup. No wrapper
  layer; `m3-react` is not on this path (it remains for React surfaces).
- **Interop**: `md-*` components render natively in the webview (custom elements
  at 100% parity across WebView2/WebKitGTK/WKWebView — [Custom Elements
  Everywhere], [Why I'm betting on the browser]).

### 5.3 Build: Bun → `frontendDist`

- `tauri.conf.json`: set `build.frontendDist` to the Bun build output (e.g.
  `../<console>/dist`) and `build.beforeBuildCommand` to `bun run build`; set
  `build.devUrl` to the Bun dev server for HMR (pattern:
  [`architecture.md`](architecture.md) §5, [`aphrody-integration.md`](aphrody-integration.md)
  §5). `tauri-codegen` embeds the built `dist/` into the binary in release
  ([`architecture.md`](architecture.md) §5) — one self-contained binary, no Node,
  no runtime server.
- The static-only requirement is satisfied trivially: Vanilla/Lit (and
  Solid/Svelte, if chosen) are SPA/MPA with no SSR ([Tauri Frontend
  Configuration]). There is nothing to opt out of (unlike Next/Nuxt/SvelteKit,
  which need SSR explicitly disabled).
- IPC: the frontend calls `window.__TAURI_INTERNALS__.invoke` /
  `@tauri-apps/api`'s `invoke` for commands; for streaming (chat / agy-loop /
  SSE) it consumes a Tauri `Channel` via a JS callback
  ([`architecture.md`](architecture.md) §2.3). If a Lit/vanilla frontend prefers
  globals over ESM imports, set `app.withGlobalTauri: true`
  ([`architecture.md`](architecture.md) §4).

### 5.4 Net effect on the phased plan

- **Phase 0 / Phase 1 unchanged** (`crates/aphrody-capture`, `crates/aphrody-app`
  shell, the single `aphrody_exec` command — [`README.md`](README.md) §6).
- **Phase 2 simplified**: "verify the M3 components render on WebKitGTK,
  WebView2, WKWebView" stays, but "build the frontend" is *reuse `apps/console`'s
  static build*, not author a framework app. Add `Channel`-based streaming in
  plain TS.
- **No new heavy dependency** enters the *frontend* tree: Vanilla/Lit adds no
  framework runtime, so the webview payload stays minimal — reinforcing the
  build-exclusion rationale (R4, [`risks.md`](risks.md) §4) on the JS side just
  as it does on the Rust side.

## 6. Summary

The shell is Tauri v2; this doc fixes the layer inside it. Because the M3
investment lives in **framework-agnostic custom elements** (Material Web/Lit)
plus **plain CSS tokens** (`@aphrody-code/theme`), and because every modern JS
framework now reaches those at 100% interop, the right choice is the **lightest
layer that adds nothing between the custom elements and the webview**:
**Vanilla TS + Lit/Material Web** (the existing console model), with **Lit-as-
app-framework** as the in-lane upgrade and **SolidJS / Svelte 5** as the
mainstream-framework alternative. **React 19 + m3-react** is demoted (heaviest
runtime, wrappers now redundant) and the **Rust→wasm** frontends are declined
for this webview (off-toolchain, heaviest WebKitGTK cold-load, hand-wired Lit
interop). This keeps the Linux #1 cold-start minimal, reuses the M3 fusion
verbatim, stays on the Bun toolchain, and matches aphrody's headless,
scriptable ethos — while insulating the project from Material Web's
maintenance-mode status by depending on the platform, not a heavy wrapper.
